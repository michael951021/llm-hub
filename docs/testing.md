## 2. What each suite is actually for

Some of these tests are boilerplate coverage; a handful are specifically earning their keep by proving something that could otherwise fail silently:

- **`packages/db/src/rls.test.ts` — "hides other orgs' nodes even from an explicit query" and "returns nothing when no org is set".** These are the suite's real payload. The first proves RLS isn't just filtering the *application's* queries — it rewrites even a query that explicitly asks for another org's `org_id`, so a bug in application-level filtering can't leak data. The second proves the `modelhub_app` role genuinely cannot bypass RLS at all: querying through plain `db` (no `withOrg`, no `app.current_org_id` set) returns zero rows rather than erroring or returning everything. That is the actual security boundary of the whole multi-tenant system, verified by an executing test against a real Postgres role, not asserted by inspection of a migration file.
- **`packages/core/src/memory.test.ts`** — the fixtures for cuda/metal/cpu headroom, OS reserve, and the "wired limit vs. 75%-of-physical fallback" branch are the only executable spec for the memory-safety math the rest of the system (and eventually a scheduler) depends on. Each fixture works out the expected number by hand in a comment (e.g. `min(96 GiB, 128 − 19.2 GiB) = 96 GiB`), so a regression shows a concrete wrong number, not just "assertion failed."
- **`apps/control-plane/src/rpc/enroll.test.ts` — "does not consume the pairing code when enrollment fails on a duplicate key."** This proves a specific, easy-to-get-wrong failure mode: if a pairing code were burned by a failed enrollment attempt, an operator would have to mint a new one for a simple retry. The test registers a key once, retries the *same* code with the same (now-duplicate) key, confirms failure, then confirms the same code still redeems for a *different* key. That's the actual guarantee, not just "duplicate keys are rejected."
- **`apps/control-plane/src/rpc/enroll.test.ts` — "maps a concurrent duplicate-key race to EnrollmentError for the loser."** Two valid pairing codes race the same public key through `enrollNode` directly (bypassing HTTP, to assert on the real error type). The app-level pre-check (`ownerDb.select` before insert) takes no lock, so both requests can pass it before either `INSERT` commits — this test exists specifically to prove the database's `nodes_public_key_idx` unique-violation path is reached and *mapped* to `EnrollmentError` with the right message, not left as an opaque driver error. `expect(fulfilled).toHaveLength(1)` — exactly one winner, not "no crash."
- **`apps/control-plane/src/rpc/connect.test.ts` — "rejects a stream with no node authorization, and writes nothing."** Captures device and node rows *before* a full Hello→Inventory→Samples sequence is sent with no auth header, confirms the RPC rejects, then re-reads the same rows and asserts byte-for-byte equality with the "before" snapshot. This is what proves `authenticateNode` really runs before a single message is processed — not just that the RPC eventually errors, but that zero side effects occurred first.
- **`apps/control-plane/src/rpc/node-auth.test.ts` — the corrupted-stored-key case.** Not attacker-reachable (an attacker doesn't control the database row), but it proves that a data problem (bad migration, manual edit, wrong-length key) fails as a clean `NodeAuthError`, logged with the node id, rather than an unmapped OpenSSL exception reaching a public unauthenticated endpoint.
- **`agent/internal/config/identity_test.go` — `TestKeyringAccountDiffersByConfigDir`.** A named regression test for a real bug fixed in Task 19: the keychain account used to be a fixed string regardless of config directory, so re-enrolling after uninstall (or running two agent instances) silently reused the same stored key. This test pins the fix.
- **`agent/internal/config/identity_test.go` — `TestKeyringIdentityWrapsBothErrorsOnDoubleFailure`.** Forces both the keychain (mocked to fail) and the file fallback (an unwritable path) to fail simultaneously, and asserts the resulting error mentions the *keychain* failure specifically — not just "something failed" — because that's the one a user with a locked keychain actually needs to see.
- **`e2e/smoke.test.ts` — the whole file, but specifically the "online" assertion.** This is the only place in the repo that exercises `authenticateNode()` accepting a **real** Go-signed header: built in Go with `base64.RawURLEncoding` (`agent/internal/transport/auth.go`), verified in TypeScript with `node:crypto.verify()` (`node-auth.ts`), over a real h2c `NodeService.Connect` stream produced by the compiled binary. Every other auth test on either side constructs its own header in-language and only proves that language's half. If this test passes, the two implementations are provably wire-compatible; if it's ever skipped or deleted, wire-compatibility between the Go and TS auth implementations stops being tested by anything.
- **`e2e/smoke.test.ts`'s keychain cleanup (`cleanUpMacKeychainIdentity`)** isn't a test of application behavior. It deletes the login-keychain entry the compiled agent wrote for this run's temp config directory, reproducing the account name from `identity.go`'s derivation in TypeScript. Without it every run on a Mac would leave one permanent keychain entry behind. It is deliberately non-fatal and darwin-only.

## 3. What is guaranteed to work

Claims below are things a reader can rely on, each tied to executing evidence — with the "proven vs. reviewed-only" distinction made explicit where it matters.

- **The row-level security boundary is real, not just configured.** Proven by `packages/db/src/rls.test.ts` running against a real Postgres instance through the actual `modelhub_app` role — not inspected from the migration SQL.
- **`computeBudget`'s arithmetic is correct for every case it has a fixture for** (cuda headroom + floor, metal wired-limit vs. 75%-fallback vs. interactive reserve, cpu OS reserve, pressure gating, zero/negative-safety invariants). Proven by `packages/core/src/memory.test.ts`, 12 tests with hand-derived expected values.
- **Node authentication rejects every malformed or malicious header shape it's been given a test for**, and — critically — the Go and TypeScript implementations of the signing/verification scheme are mutually compatible. The former is proven by `node-auth.test.ts` (in-language) and `auth_test.go` (in-language); the latter is proven only by `e2e/smoke.test.ts`, which is the sole test that puts a real Go-built header in front of the real TS verifier.
- **A pairing code can be redeemed exactly once, survives a rejected duplicate-key attempt without being burned, and a race between two codes for the same key produces exactly one winner with a mapped, non-opaque error.** Proven by `pairing.test.ts` and `enroll.test.ts`.
- **An unauthenticated `Connect` attempt writes nothing to the database, verified by an explicit before/after row comparison, not an assumption of a clean starting state.** Proven by `connect.test.ts`.
- **The offline-liveness sweep's threshold math (degraded at three missed heartbeats, offline at six — 15s and 30s at the default 5s `SAMPLE_INTERVAL_MS`, ordering so a long-silent node lands on `offline` not `degraded`) is correct**, proven twice: in isolation with an injected clock (`connect.test.ts`), and against a real killed agent process with a real elapsed-time comparison (`e2e/smoke.test.ts`).
- **The CPU probe, and on macOS the Metal probe, produce internally consistent, in-range data** (`TestProbeConformance`, which runs `DefaultProbes()` for whatever platform CI or a developer's machine actually is). On Linux CI this covers the CPU probe only (Metal is `//go:build darwin`).
- **The NVML (CUDA) probe compiles under its build tag and is reviewed, but has never executed against real NVIDIA hardware in this codebase's test history.** `probe_nvml.go` is excluded from every default build (`//go:build nvml`, and CI's `go` job never passes `-tags nvml`); it's only built in `agent/.goreleaser.yaml`'s `agent-cuda` release target, which this repo has no test for either. Nothing in `conformance_test.go` — which would otherwise catch a probe returning zero `TotalBytes` or a duplicate `LocalID` — has ever run this file. Treat any claim about NVML behavior as **verified by review only**, not by an executing test.

## 4. What is not tested

An honest accounting of gaps, found by reading rather than assumed:

- **The NVML probe's actual runtime behavior against real NVIDIA hardware.** See Section 3 — it has never executed, by build tag exclusion, in any CI job or local run recorded in this repo.
- **The macOS Metal probe under real memory pressure.** `TestProbeConformance` exercises `metalProbe` on a real Mac (when run there) but the fixture data depends on whatever pressure state the machine happens to be in at test time. Notably, the probe *was* observed returning `warn` for `kern.memorystatus_vm_pressure_level` on a real development machine during this slice's work — genuinely useful evidence that the sysctl-reading code path works — but that was an incidental observation, not a repeatable, asserted test case. There is no test that forces or simulates `warn`/`critical` pressure and asserts the probe reports it correctly.
- **The `/healthz` 503/degraded path.** `app.test.ts` only asserts the healthy 200 case. A throwaway test forcing a database or Redis failure to check the 503 response was written once during development and then deleted; the code path (`app.ts`'s `Promise.all` over db/redis pings, falling back to `"degraded"`/503) exists but nothing currently exercises it.
- **`FleetService.GetNode`.** The RPC method is implemented in `rpc/fleet-service.ts` and registered through `router.service(FleetService, {...})` like every other method, but `fleet.test.ts` only tests `ListNodes` and `CreatePairingCode` — no test calls `GetNode` at all. The web app never calls it either (`apps/web/src/routes/fleet.tsx` only uses `listNodes`); it has no browser-facing route or component consuming it. It is live, callable code with zero test coverage and zero current callers.
- **The web app beyond three component suites.** `DeviceMemoryBar.test.tsx`, `NodeCard.test.tsx`, and `sign-in.test.tsx` are the entirety of component-level testing (`format.test.ts` is a plain unit test, not a component test). There is no test for `routes/fleet.tsx` itself (the data-fetching + list-rendering route), `AddNodeDialog.tsx`, `sign-up.tsx`, `routes/root.tsx`, or `router.tsx`. There is **no browser automation of any kind** — no Playwright/Cypress/similar — so nothing proves the app actually renders correctly in a real browser, that routing works end-to-end, that the Vite dev proxy config is correct, or that a real sign-in flow reaches the fleet page.
- **The self-heal double-failure path.** `auth/session.test.ts`'s "self-heals a session left with no organization" test proves `requireSession`'s self-heal *succeeds* when the original org row is gone. Nothing tests what happens if `ensurePersonalOrganization` *itself* fails during that self-heal attempt (the `catch` block in `session.ts` that sets `orgId = null` and eventually throws a 403) — that's a real code path (visible in `session.ts`'s try/catch around the self-heal call) with no test forcing it.
- **The CI workflow itself, on real GitHub runners.** Nothing in this repo tests `.github/workflows/ci.yml` — its correctness (service container health checks, env var wiring, job ordering, the Go-toolchain version match between the `typescript` and `go` jobs) is verified only by it actually running on pushes/PRs, which is outside this repo's own test suites.
- **Multi-node or multi-GPU behavior of any kind.** Every test that involves a node population (`fleet.test.ts`'s org-isolation check, `rls.test.ts`) uses at most two nodes to prove isolation, not fleet-scale behavior. No test enrolls or connects more than one node concurrently to prove the control plane handles a real fleet (concurrent `Connect` streams from many agents, `ListNodes` pagination — there is none — or contention on `offline-sweeper.ts` at scale). Every device-level test (`connect.test.ts`, `DeviceMemoryBar.test.tsx`) uses exactly one GPU; nothing proves a multi-GPU node's inventory upsert/delete-stale logic (`recordInventory`'s `notInArray` deletion) behaves correctly when some devices vanish and others don't across a larger set.

## 5. Known weaknesses in the tests themselves

Places a test could pass for the wrong reason, or where coverage reads deeper than it is:

- **Several `node-auth.test.ts` cases assert only the error *type*, not the reason.** "rejects an unknown node id" and "fails safely...when the stored public key is corrupted" both assert `rejects.toThrow(NodeAuthError)` with no message match. Contrast this with "rejects a signature made with the wrong key" (`/signature/i`), "rejects a timestamp outside the skew window" (`/timestamp/i`), and "rejects a replayed nonce" (`/replay/i`), which do check the message. A future change that made an unknown-node-id request throw `NodeAuthError("stored node key is invalid")` (the *wrong* branch) would still pass the "unknown node id" test — it only checks that *some* `NodeAuthError` came out, not the right one.
- **`TestProbeConformance`'s coverage is only as good as the platform it runs on.** The single test function fans out into subtests via `DefaultProbes()`, so its actual coverage silently varies by machine: a Linux CI run only ever exercises the CPU (and, if a driver happened to be present and the binary were built with `-tags nvml`, CUDA — which CI never does) probe; the Metal probe only runs on a developer's Mac. Nothing in the suite fails loudly to say "the Metal probe was skipped on this run" — a change that broke `probe_darwin.go` would show green on every CI run indefinitely, only surfacing on a Mac developer's local `go test`.
- **The e2e suite's liveness-sweep assertion assumes the sweep already left the node non-`offline`.** `smoke.test.ts`'s second test kills the agent and calls `sweepOfflineNodes` with a clock pushed past `OFFLINE_AFTER_MS`; it does not independently verify the node was `online` immediately before the kill (it relies on the first test having left it there), so a bug that left the node in some other state between the two tests could produce a false pass on "marks the node offline" for the wrong reason (already-offline, not newly-offline).
- **`app.inject()`-based tests exercise real handler and domain logic but zero real transport.** As noted in the codebase guide's traps section, most control-plane suites never touch a socket, HTTP/2 framing, or real header serialization. This isn't a bug in the tests, but it means the bulk of "green" control-plane coverage is a weaker signal about wire-level correctness than the test count alone suggests — only `connect.test.ts` and `e2e/smoke.test.ts` close that gap.
- **`DeviceMemoryBar.test.tsx`'s "no divide-by-zero" test only checks the `available` segment's width.** It doesn't assert on the other three segments (`managed`, `foreign`, `headroom`) under the same zero-total condition, so a divide-by-zero introduced in one of those specifically wouldn't be caught by this test.

## 6. Priority list for closing the gaps

Ordered by how much silent risk each gap carries relative to how cheap it is to close:

1. **Add a `GetNode` test, or remove the method.** Zero-cost either way (it's already implemented and registered), and dead, untested, uncalled RPC surface is exactly where a future change introduces a bug nobody notices — either give it the same session/org-isolation tests `ListNodes` has, or delete it until slice 2 actually needs it.
2. **Re-add a `/healthz` degraded/503 test.** One existed and was deleted; restoring it (mock/force a DB or Redis failure and assert the 503 + `"degraded"` body) closes a gap in a route that operators will depend on for monitoring.
3. **Test the self-heal double-failure path in `requireSession`.** A user hitting this path currently gets a silent, permanent 403 with no test guarding the error message or behavior — force `ensurePersonalOrganization` to fail (e.g. inject a slug collision) and assert the resulting error is legible, not just "some 403."
4. **Strengthen the weak `node-auth.test.ts` assertions to check messages, not just error type.** Cheap (change two `toThrow(NodeAuthError)` calls to message-matching), and closes the specific "wrong branch, same exception class" blind spot in Section 5.
5. **Add at least one browser-automation smoke test for the web app** (a single Playwright test: sign up, mint a pairing code, see it rendered) — this is the largest true gap in the web app, since currently *nothing* proves the app works in an actual browser, only that isolated components render given hand-built props.
6. **Add a multi-node / multi-GPU test.** At minimum, extend `connect.test.ts` or add a new suite proving `recordInventory`'s stale-device deletion behaves correctly with 3+ devices where some are removed and some aren't, and that two nodes' concurrent `Connect` streams don't cross-contaminate each other's device rows. This is the most direct predictor of correctness once slice 2+ starts scheduling across a real fleet.
7. **Get an NVML-tagged build into CI, even without real hardware.** At minimum, add a CI step that runs `go build -tags nvml ./...` (compile-only, no test) so a change to `probe_nvml.go` can't silently stop compiling; actual runtime behavior against real hardware will remain unverified until this project has NVIDIA CI runners, but compilation is cheap to guarantee today.
